# Roadmap

MukiDoc 的发展路线围绕一个目标展开：从一套清晰的软件工程文档方法，逐步发展成一套能够被人和 AI 稳定使用、自动维护并长期演化的开发体系。

## 1. Methodology

建立 MukiDoc 的基础方法论。

这一阶段需要明确整套文档体系的职责、边界和层级关系，并完成主要文档类型的 Design。核心是形成稳定的项目认知结构，以及 Design、System Design、Implementation 三层之间的解耦关系。

这一阶段完成后，MukiDoc 应该能够仅依靠文档规范指导一个项目从高层意图逐步走向具体实现。

## 2. Documentation Specification

把方法论进一步整理成完整、可执行的文档规范。

需要确定每种文档应该表达什么、如何组织、有哪些约束，以及不同文档之间如何共同构成一个完整的软件工程上下文。

同时建立适用于所有文档的统一写作和维护规则，使不同项目、不同开发者和不同 AI 生成的文档仍然保持一致。

## 3. Agent Workflow

设计 AI 在 MukiDoc 项目中的工作方式。

这一阶段需要明确 AI 如何读取项目上下文、如何根据需求定位受到影响的文档、如何逐层完成设计和实现，以及如何在修改代码时同步维护相关文档。

目标是让 MukiDoc 从“人按照规范写文档”发展成“人提出需求，AI 按照体系持续维护项目”。

## 4. Tooling

将稳定的方法和工作流逐步实现为工具能力。

工具负责帮助项目初始化 MukiDoc、提供文档模板和规则、辅助 AI 获取正确上下文，并检查文档结构、完整性和一致性。

这一阶段不改变 MukiDoc 的方法本身，而是降低使用和维护它的成本。

## 5. Validation

通过真实软件项目持续验证 MukiDoc。

重点观察这套体系能否在长期开发中保持上下文完整，能否让新的 AI 快速接手项目，三层设计是否能够有效减少耦合，以及文档同步是否真正降低人的认知负担。

验证得到的问题应反过来推动方法、规范和工具继续调整。

## 6. Reusable Development System

最终，MukiDoc 应形成一套可以跨项目复用的人机协作开发系统。

开发者能够用稳定的方式建立项目、表达设计、提出需求和检查结果；AI 能够理解项目、持续开发并同步维护上下文。项目本身保存足够完整的软件工程知识，不依赖特定开发者、特定 Agent 或历史对话才能继续演化。

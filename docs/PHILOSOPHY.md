# MukiDoc Philosophy

**处境与问题。** 传统软件开发中，很多重要知识并不真正存在于项目里，而是散落在人脑、代码、会议和临时对话中。需求、设计、系统结构和具体实现也很容易混在一起：一个想法很快落到代码，一次实现选择逐渐反过来定义系统本身。项目越大，理解项目就越容易变成理解代码，修改系统也越来越依赖开发者对大量细节的记忆。

AI 改变了这种关系。当代码可以被快速生成、修改和重构之后，人真正稀缺的工作开始向上移动。相比亲自完成每一个实现细节，更重要的是理解问题、形成设计、建立结构、做出取舍，并判断最终结果是否真的符合最初的意图。

**需求与想法。** 因此，我们希望建立一套从一开始就面向人和 AI 共同开发的方法。人不再主要通过直接操作代码控制项目，而是通过更稳定的文档表达意图、设计和判断；AI 根据这些上下文继续细化并完成实现，同时维护代码与文档之间的一致性。

这里的文档不是开发完成后的说明书，而是开发过程本身的一部分。它既服务于人理解和思考项目，也服务于 AI 获取足够完整、稳定的上下文。

**需求本质。** 真正的问题并不是怎样让 AI 更会写代码，而是怎样让一个软件项目的重要知识不依赖某个人、某一次对话或某一版代码存在。

一个完整的软件项目不仅需要知道“现在代码是什么样”，还需要保留它是什么、为什么存在、为什么这样设计、内部怎样组织、当前怎样实现、做过哪些重要决定、经历了什么变化，以及最终结果是否真的有效。只有这些上下文被持续外化，新的开发者或新的 AI 才能重新进入项目，而不需要从代码和聊天记录里重新考古。

与此同时，这些知识也不能混成一层。我们想要什么、系统内部怎样工作、当前具体怎样实现，本质上是三个不同的问题。把它们混在一起，会让上层设计过早绑定下层技术，也让任何修改都牵动整条链路。

**核心思路。** 这套方法首先是一套为人机协作设计的软件工程方法。人主要负责理解问题、形成意图、建立抽象和做出判断；AI 主要负责继续细化这些决定、完成实现，并在开发过程中维护项目状态的一致性。文档处在两者之间，成为共同的上下文和主要协作界面。

它同时试图把软件工程所需要的关键上下文保存在项目本身，而不是依赖外部记忆。一个项目应该能够通过自身的文档说明它的目标、思想、整体结构、设计、实现状态、演化过程和实际结果。这样代码可以变化，AI 可以更换，对话可以结束，但项目的核心认知仍然能够延续。

在具体设计上，最核心的是 Design、System Design 和 Implementation 三个连续但彼此解耦的层次。

Design 描述被创造出来的东西本身应该是什么样，关心它的功能、规则、行为和领域性质，而不预设内部必须怎样实现。

System Design 描述为了实现这些设计，内部系统应该怎样组织和运行。它把外部设计转化为系统结构、状态、关系和运行机制，但仍然保留具体技术方案的自由。

Implementation 再把这些系统设计落实到当前具体的工程环境中，决定真正采用怎样的技术和实现方式。

三层形成逐步细化的关系：上一层定义什么必须成立，下一层决定怎样让它成立。同一个 Design 可以存在不同的 System Design，同一个 System Design 也可以存在不同的 Implementation。低层级的设计，同时也是高层级设计的一种实现。

这种分层并不是为了给“设计”和“实现”划一条绝对边界，而是为了让不同抽象层级的决定彼此解耦，使项目能够在保持上层意图稳定的同时，自由演化下面的系统结构和具体实现。

**如何运转。** 一个新的需求出现后，人先明确真正想得到什么，再和 AI 一起逐层细化为系统设计和实现方案；信息足够清楚后，AI 完成代码，并同步更新受到影响的文档，人主要检查这些文档是否仍然准确表达项目。系统运行和 Evaluation 又会产生新的事实，如果结果不符合预期，就判断问题属于设计、系统设计还是具体实现，修正对应层级，再让 AI 继续向下同步，由此形成持续迭代的开发循环。

**为什么有效。** 这种方式把原本需要同时掌握的复杂问题拆到不同抽象层级，人可以只关注当前真正重要的判断，而随着设计逐层明确，AI 需要自行猜测的空间也越来越小；与此同时，完整上下文被保存在项目内部，使新的 AI 或开发者能够重新建立理解，而不依赖某个人的记忆。人因此可以把更多精力放在意图、结构和取舍上，把大量展开、实现、同步和重复性工程工作交给 AI，同时仍然保持对项目的控制。

**原则与思路。**

1. 软件工程的重要上下文应尽可能存在于项目本身，而不是依赖人的记忆、临时对话或某一版代码。
2. Design、System Design 和 Implementation 应保持清楚的抽象层级和解耦关系，上层定义语义，下层决定实现方式。
3. 文档是人与 AI 的主要协作界面，也是项目长期存在的共享状态；代码是这些设计在当前条件下的具体实现。
4. 人主要负责问题、意图、判断和取舍，AI 主要负责细化、实现、同步和执行。
5. 文档与代码应共同演化。开发改变了系统，也应同步改变描述系统的知识。
6. 实现不是终点，实际运行和 Evaluation 产生的新事实应持续反馈到正确的设计层级，推动下一轮迭代。

最终，这套方法希望让项目的意图、结构和知识始终掌握在人手中，同时让 AI 承担从清晰设计到具体实现之间越来越多的工作。

# AGENTS.md Design

AGENTS.md 是 MukiDoc 面向 AI Agent 的项目级工作协议，位于仓库根目录，由 MukiDoc 维护。

它将 MukiDoc 中分散的 Design 和规则“编译”为一份适合 Agent 长期加载的高密度上下文。编译时保留会影响 Agent 理解、判断和行为的信息，省略不影响这些能力的推导、解释、例子和其他面向人的展开内容。

AGENTS.md 必须能够独立使用。采用 MukiDoc 的其他项目可能只获得这一份协议，无法访问 MukiDoc 自身的规范文档；协议应包含建立、维护和评价整套文档体系所需的信息，而当前项目的具体目标、设计和事实由该项目自己的文档保存。

编译以语义覆盖为目标，不预设行数上限。每类文档的职责、内容范围、固定结构、必要的篇幅和格式约束、创建与更新条件，以及容易混淆的边界都应保留。省略的是不影响理解和行为的重复、讨论过程与展开说明；设计理由或例子如果是独立判断所必需的，也应保留。检查编译结果时，应逐项对照源规范，并判断一个未读过源规范的 Agent 是否会因缺少信息而做出偏离设计的结果。

协议必须明确区分固定骨架与按需内容：基础目录及骨架文档即使暂时为空也必须存在，Area 和可选文档按需创建。检查时不能以“尚无内容”为由忽略固定入口缺失，也不能为补齐结构编造正文。

交付的协议应带可识别版本，与初始化 Skill 的版本分开维护。初始化时可以识别旧版并询问是否更新；已有文件默认保留，确认替换前说明实际差异并备份原文。同版本地修改、无版本标记和更高版本不应被笼统当作旧版。协议更新只改变工作规则，不代表目标项目知识已经完成迁移。

AGENTS.md 应充分信任 Agent 的理解、推理和执行能力。它提供项目地图、语义边界和重要约束，但尽量不规定固定流程、阅读顺序或具体做法。只约束真正不能被破坏的东西，其余部分交给 Agent 根据当前任务自主判断。

全文分为五部分：

**Role → MukiDoc → Design → Develop → Evaluate**

### Role

定义 Human 和 Agent 的基本关系，以及 Agent 在项目中的自主权。

核心是让 Agent 明白：

* Human 和 Agent 共同参与项目，也共同维护项目知识。
* Human 更关注需求、方向、判断和最终意图。
* Agent 可以主动参与分析、设计、实现、调查、测试、评价和文档维护。
* Agent 应利用自己的能力解决问题，而不是机械执行预设步骤。
* 当需求已经足够明确时，应自主推进；真正涉及方向、意图或无法合理推断的问题，再交回 Human 判断。

这一部分首先建立的是信任和协作关系，而不是权限清单。

### MukiDoc

让 Agent 快速理解自己所处的知识体系。

这一部分应浓缩 MukiDoc 的整体架构，使 Agent 知道 Project Context、Design Chain、Information、Evaluation 等部分分别保存什么性质的知识，以及哪些内容代表当前状态、哪些内容属于历史、证据或辅助上下文。

这里不规定“先读什么再读什么”。Agent 根据当前任务自行决定需要读取多少上下文，并避免为了安全感无差别加载整个文档目录。

同时应让 Agent 理解不同知识的性质和权威性，避免把历史调查、实验结果或原始资料误当作当前正式设计。

### Design

编译所有与“形成和维护项目知识”有关的规则。

需要包含：

* Design、System Design、Implementation 三层的含义和边界。
* Project Context 各类文档最核心的职责。
* Information 不同类型信息的用途。
* 文档修改、组织和写作的通用规则。
* PHILOSOPHY、ARCHITECTURE、ROADMAP、DECISION、DEVLOG 等特殊文档最关键的结构约束。

这里不复制完整 Document Design，而是把其中足以保证 Agent 正确写文档的规则压缩进 AGENTS.md。

Agent 应能够自由决定文档如何具体展开，但不能破坏抽象层级、文档职责和已经定义的结构约束。

### Develop

定义 Agent 改变实际项目时需要维持的关系。

重点是保持设计、项目知识和实际实现之间的一致，而不是规定开发步骤。

Agent 可以自行选择实现方式、调试方法、工具和任务拆解方式；Implementation 层应给予较大的工程自由度。越接近项目上层意图，越需要谨慎，不应为了让代码更容易实现而自行改变 Design。

开发过程中产生的新知识应进入最合适的位置。正式结论、调查过程、实验结果、关键决策和项目级开发历史各自有不同归属，不应全部堆进同一种文档。

代码和现实系统发生有意义的变化后，已经因此失真的文档也应同步更新。

### Evaluate

让 Agent 不只判断“代码是否运行”，还判断各层承诺是否真正成立。

Agent 应根据任务自主选择合适的验证手段。

Evaluation 可以来自 PHILOSOPHY、Design、System Design 和 Implementation。当前交付的 AGENTS.md 暂不编入尚未落地的 MukiCheck 内容与目录约定，待其可用后再纳入。评价失败时，应分析问题真正产生在哪个层级，再修正对应内容，而不是单纯为了让检查通过而局部打补丁。

Evaluation 本身同样不规定统一执行方式。测试、脚本、benchmark、Agent evaluation、人工判断或真实使用反馈都可以成为证据。

AGENTS.md 最终应做到两件事：让一个新的 Agent 很快理解这个项目中的知识世界和基本规则，同时不给它施加不必要的流程约束，使强模型能够充分利用自己的能力自主完成工作。

# Bootstrap Design

Bootstrap 为新项目或已有项目建立 MukiDoc 的固定知识入口。用户指定目标项目后，获得完整目录骨架、骨架文档和可独立使用的 Agent 协议；随后可以在这些位置逐步形成项目知识。

### 初始化结果

根目录 README.md、AGENTS.md，docs 下七份 Project Context 文档，以及三层设计链、Information 四个分类、Evaluation 四个承诺来源的目录均须存在。固定文档暂时没有内容时只保留标题，空目录需要能够随项目保存。Area、具体设计文档、Evaluation Suite 和可选文件不预建；尚未落地的 MukiCheck 不纳入初始化。

已有文件保留原样，包括已存在但为空的骨架文档。重复初始化只补缺失项，不重写正文、不清理已有内容。初始化不生成项目事实，不推断意图，不将已有代码自动转成设计承诺。

### 使用方式

用户可以通过初始化 Skill 请求建立骨架，也可以直接运行同一套初始化程序。两种入口具有相同的文件行为。Skill 负责确定目标、解释结果和处理协议更新选择，程序负责稳定地执行文件操作。预览模式只展示计划，不改变项目。

初始化包整体可独立使用，不要求目标项目能够访问 MukiDoc 的源规范，也不依赖网络下载当前协议。用户能知道初始化包提供的版本，以及实际创建、保留和仍待决定的内容。

### 协议版本

AGENTS.md 携带独立的协议版本，初始化包自身也有版本。两者可以独立演进：初始化行为变化不一定改变协议，而协议规则变化需要提升协议版本。

目标没有 AGENTS.md 时安装内置协议。目标与内置协议完全一致时保留；能识别出旧版本时提示用户是否更新。版本相同但内容不同、没有可识别版本、目标版本更高应分别表达，不把所有差异归为过期。

覆盖已有协议需要针对该次替换的明确授权。先说明实际差异及对项目附加规则的影响，再让用户决定；已明确授权时不重复询问。确认替换后完整备份原文件，再写入内置协议。拒绝或未确认不影响其余骨架的补齐。目标版本高于内置版本时保留，不降级。

更新默认替换完整协议，不自动合并项目特有规则。无版本的早期协议不能凭内容相似猜测版本；可在明确确认后按替换处理。审查与执行之间原文件变化时，应重新核对实际差异，不能覆盖未经审查的新内容。

### 与迁移的边界

已有项目可以补齐结构，但旧文档的分类、改写、归档及知识补充属于迁移。协议更新也不等于项目文档已经符合新规范。完成初始化仅表示固定骨架已建立、原有内容得到保留，并且协议安装或保留的状态明确。

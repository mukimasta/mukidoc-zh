# MUKICHECK Evaluation Design

MukiCheck 是所有 MukiDoc 项目自带的项目健康检查。它关注项目知识是否正确、清晰、自洽，是否与真实代码保持一致，以及这些文档最终能不能真的帮助一个陌生 Agent 理解并继续项目。

MukiCheck 评价的是“采用 MukiDoc 后，这个项目的知识体系是否健康”。项目本身的产品目标、用户体验和业务效果是否成功，仍由项目自己的 Evaluation 负责。

MukiCheck 分为三个层次：

**静态文档检查 → 文档–代码联合检查 → 动态理解检查**

前一层关注知识本身，后一层逐渐加入真实工程和真实使用。三层共同判断 MukiDoc 是否仍然能够承担项目长期上下文。

## 静态文档检查

静态检查只读取 MukiDoc，判断当前保存的项目知识本身是否健康。

### 规范正确性

首先检查能够明确规则化的约束，例如文件结构、命名、篇幅、标题层级、列表格式以及各类文档规定的固定结构。

这一层解决最基础的问题：文档是否按照 MukiDoc 的规范存在。它应尽量确定、客观，也为后面的语义检查排除低级错误。

### 位置与层级正确性

进一步检查知识是否待在正确的位置。

即使一段内容本身完全正确，放错文档或抽象层级仍然会破坏整个知识体系。Design 不应该被具体实现绑住，Implementation 不应该承担上层产品设计，历史、调查、实验和正式设计也应该保持各自的性质。

这一层关注的是 MukiDoc 的知识分类是否仍然成立，以及内容是否随着成熟和变化进入了更自然的位置。

### 内部一致性

检查所有正式文档组合起来是否仍然描述同一个项目。

单篇文档可以各自正确，但 Architecture、Design Chain、Project Context 等内容之间仍可能发生矛盾、遗漏和漂移。同一个概念也可能逐渐出现不同定义，历史状态可能和当前状态混在一起。

这一层保证 MukiDoc 最终形成的是一个统一的项目知识系统，而不是一组各自成立的 Markdown 文件。

### Philosophy 对齐

静态检查的最高层回到项目自己的 PHILOSOPHY。

PHILOSOPHY 描述项目最核心的目的、思想和长期判断依据。后续设计即使格式正确、彼此一致，也可能已经在长期迭代中逐渐偏离最初真正想解决的问题。

这一层检查当前文档所表达的项目方向，是否仍然符合自己的核心 Philosophy。它只能判断“当前设计是否符合所声明的 Philosophy”；这些 Philosophy 在真实使用中是否真的有效，仍需要项目自己的 Evaluation 验证。

## 文档–代码联合检查

静态文档健康以后，MukiCheck 将真实代码加入判断，检查文档描述的架构、行为、系统机制和实现约束是否仍然真实存在于工程中，同时检查代码里已经形成的重要结构和机制是否已经沉淀回对应文档。它关注的是双向一致性：文档不能描述一个已经不存在的系统，代码也不能在长期演化后悄悄产生大量只存在于实现里的项目知识。

## 动态理解检查

动态检查通过一个没有历史聊天和隐含上下文的新 Agent，通常是 Subagent，只依赖当前项目保存的文档重新理解项目，验证 MukiDoc 是否真的承担了项目上下文。它重点观察这个 Agent 能否正确理解项目目标、核心 Philosophy、整体架构和主要设计，能否找到正确的知识位置，能否面对一个新需求判断大致影响哪些层级，以及在文档不足时能否明确识别不确定性而不是自行脑补。它最终回答的是：把当前项目交给一个完全陌生的 Agent，它能不能仅依赖 MukiDoc 正确理解这个项目，并具备继续工作的基础？

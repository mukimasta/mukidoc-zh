# ROADMAP Design

ROADMAP 用来描述项目长期发展的主要阶段，以及这些阶段如何一步步把项目带到最终目标。它关注的是项目能力和成熟度的演进，不负责维护当前进度。

ROADMAP 应保持相对静态。只有整体发展路径发生变化时才修改；实际完成了什么、开发过程中发生了什么，由 DEVLOG 持续记录。

阶段应按照**能力或成熟度的质变**来划分，而不是按照功能、组件、任务或版本名称划分。每完成一个阶段，项目都应该获得一种此前没有的重要能力，并自然成为下一阶段成立的基础。

每个阶段主要说明：

1. 当前阶段要解决的核心问题。
2. 完成这一阶段后，项目会获得什么新的能力或状态。
3. 这种变化为什么能够推动项目进入下一阶段。

各阶段应形成明确的递进关系。仅看阶段标题，也应该能够大致理解项目是如何逐步发展和成熟的；如果阶段可以任意调换顺序而不影响逻辑，它们更可能只是任务列表，而不是 Roadmap。

好的阶段划分通常像：

`Methodology → Specification → Agent Workflow → Tooling → Validation → Reusable System`

仅看标题就能看出项目从形成方法，到变得可执行、可自动化、被真实验证，最后成为可复用体系的演进过程。

不好的阶段划分常见有几种：

`Documentation → CLI → Plugin → Website → Demo → Release`

这是按要做的产物划分，本质上是功能或交付物列表，阶段之间没有明确的能力递进关系。

`Frontend → Backend → Database → API → Deployment → Monitoring`

这是按系统模块或工程领域划分，更像工作分解结构，不是项目成熟路径。

`Prototype → MVP → Alpha → Beta → Release → Future`

这是按版本名称划分。标题本身几乎不提供项目会发生什么质变，也看不出每个阶段为什么必须存在。

`Q1 → Q2 → Q3 → Q4`

这是按时间切分，描述的是排期，而不是项目能力如何演进。

判断阶段是否合理时，可以尝试删除具体任务和时间信息，只看阶段名称与阶段结果。如果仍然能够看出项目如何一步步获得新的能力，并且后一阶段明显依赖前一阶段，才更接近真正的 Roadmap。

格式固定为：

`# Roadmap`

开头使用一小段概括整条路线最终希望把项目带到什么状态。

每个阶段使用编号二级标题：

`## 1. Stage Name`

`## 2. Stage Name`

`## 3. Stage Name`

每个阶段使用 1–3 个自然段，重点描述阶段问题、能力变化和向下一阶段的推进关系，不展开具体任务和实现细节。

最后一个阶段描述项目希望最终形成的完整状态，使整条路线有明确终点。

阶段数量通常控制在 4–8 个，如复杂项目单层级讲不清楚的，可以适当使用双层级，全文不超过 2000 字。

# PHILOSOPHY Design

PHILOSOPHY 用来回答项目最上层的“为什么”。它从真实问题、需求或最初想法出发，继续追问其本质，并由此推导出项目的核心思路、这些思路如何运转，以及为什么有效。

它不负责介绍项目全貌，也不描述具体功能、模块、目录、技术方案或实现细节。它提供的是后续设计所依赖的思想基础。读完之后，读者应该能够理解项目为什么会形成现在的方向，并能够用这些思想判断未来的新方案是否符合项目本身。

全文应形成一条连续的推导链：

**处境与问题 → 需求与想法 → 需求本质 → 核心思路 → 如何运转 → 为什么有效 → 原则与思路**

**处境与问题**从真实场景或背景建立出发点，说明原本存在什么问题。建议 1–2 段。

**需求与想法**说明由此自然产生了什么需求，以及最初希望改变什么。建议 1–2 段。

**需求本质**继续向下追问，说明表面需求背后真正需要解决的问题。建议 1–2 段。

**核心思路**是全文主体，应从前面的本质问题自然推导出来，解释项目最重要的思想、方法和关系。建议 3–6 段，占全文篇幅最多。核心思想必须停留在 Philosophy 层级，不进入具体设计和实现。

**如何运转**用一个典型场景说明这些思想实际怎样发生，尤其适合描述人、系统或其他参与者之间的协作关系。固定为 1 段。

**为什么有效**回到最初的问题，说明前面的核心思路为什么能够解决它。固定为 1 段，不再引入新的核心概念。

**原则与思路**把全文已经推导出的关键思想压缩为数条原则，只做总结，不增加新的设计。最后用一句话收束全文。建议条数小于 8 条，如果思路较为复杂，可以用嵌套列表，但外层不超过 8 条。

正文以连续论述为主。每个部分使用 `**小标题。**` 直接接正文，不使用多级 Markdown 标题。只有最后的“原则与思路”使用有序列表，其他部分默认使用自然段。

各部分必须前后相接，后一部分应由前一部分自然推出。原则应该是推导的结果，而不是文章的起点。如果某个核心观点只能作为结论被接受，而无法从前文自然得到，就需要补足推理。

全文不超过 2000 字。核心思路可以充分展开，其余部分保持克制。

一篇完成良好的 PHILOSOPHY 应做到三点：让读者理解核心思想是怎样产生的；让这些思想能够指导之后的设计判断；即使具体架构、技术和实现发生变化，其中的主要内容仍然成立。

# DESIGN CHAIN Design

Design Chain 将软件设计拆成三个彼此衔接、尽量解耦的层级：

**Design → System Design → Implementation**

之所以分成三层，是因为开发中一直存在三个不同的问题：我们到底想设计一个什么东西；为了让它成立，内部系统应该怎样工作；在当前工程条件下，具体怎样把它实现出来。

如果这三个问题混在一起，上层设计很容易被某一版技术方案绑死，内部系统真正重要的结构也容易埋进代码和实现细节里。分成三层以后，上层定义稳定的语义和约束，下层在这些约束内拥有实现自由，各层也可以独立演化。

## Design

Design 描述被设计的对象本身应该是什么样。

它关注的是“最终想得到什么”，不考虑软件内部怎么组织，也不提前决定采用什么技术。只要对象本身没有变化，即使整个系统重新实现，这一层也应该大体保持稳定。

一般会写：

* 功能和能力。
* 用户或其他参与者能做什么。
* 核心行为和规则。
* 交互方式和体验。
* 领域中的核心概念及其关系。
* 对象需要保持的重要性质。
* 设计背后的主要取舍和理由。

如果缺少这一层，项目很容易从需求直接跳到技术方案。时间久了，“现在碰巧这样实现”会逐渐变成“它本来就应该这样”，具体实现开始反过来限制设计。

## System Design

System Design 描述为了实现 Design，内部系统应该怎样组织和运行。

这一层开始进入软件内部，但仍然尽量不绑定具体技术。它把对象层的设计翻译成一个能够真正运行的内部系统。

一般会写：

* 系统由哪些模块组成。
* 每个模块的职责和边界。
* 模块之间如何协作。
* 核心状态及状态变化。
* 逻辑数据模型和数据关系。
* 生命周期。
* 关键业务流程和运行流程。
* 并发、同步、错误恢复等系统级机制。
* 跨模块长期稳定的约束。

很多 System Design 会跨越多代技术实现长期存在，因此不应该和某个框架、数据库或代码结构绑死。

跨模块的数据关系可以按需集中在 `DATA_MODEL.md`，重要的动态过程可以按需集中在 `RUNTIME.md`。

## Implementation

Implementation 描述当前工程具体怎样落实 System Design。

到了这一层，才真正进入当前采用的技术和工程方案。Implementation 可以随着技术环境快速变化，只要上层设计没有改变，更换技术栈或重构工程结构都应尽可能只影响这一层。

一般会写：

* 编程语言、框架和运行环境。
* 数据库、缓存和消息系统。
* API、协议和接口契约。
* 具体数据结构和存储结构。
* 依赖库和第三方服务。
* 并发、线程和任务调度的具体实现。
* 序列化、配置和部署方式。
* 性能优化方案。
* 当前工程中的重要技术约束和约定。

项目级技术选择可以按需集中在 `TECH_STACK.md`，具体接口契约可以按需集中在 `API.md`。

## 为什么是三层

只分 Design 和 Implementation 两层通常不够，因为“内部系统应该怎样工作”本身就是一层重要而相对稳定的设计。放得太高，会让 Design 过早进入软件内部；放得太低，又会让长期稳定的系统机制和当前技术方案混在一起。

作为整个项目共同的主干，这三层刚好分别回答：

**对象是什么 → 系统怎么工作 → 当前怎么实现**

不同项目当然可以在每一层内部继续细分，但没有必要继续增加固定的主层级。

## 层级边界

判断一项内容应该进入哪一层，可以看改变它意味着什么：

1. 对象本身的行为、规则或性质发生变化，属于 Design。
2. 对象没有变化，但内部结构、状态、数据关系或运行机制发生变化，属于 System Design。
3. 系统机制没有变化，只改变工程和技术方案，属于 Implementation。

边界不要求机械精确。真正重要的是让一篇文档尽量保持在同一个抽象层级，避免下层细节逐渐渗透并绑定上层设计。

## Area

三层是纵向的固定维度；每一层内部还需要一个横向维度来组织文档，这个维度称为 Area。Area 是项目自然形成、相对稳定的问题空间，可以是一个交付物、一种产品能力、一个领域或一类系统 concern，具体由项目自身决定。

由此形成 Design Chain 的组织原则：固定 Layer，自由 Area。`design/`、`system_design/`、`implementation/` 三个层级目录必须建立并保留，即使暂时为空；Git 项目用 `.gitkeep` 保留空目录。横向的 Area 随项目生长，不预先规定，也不套用统一模板。

Area 遵循三条规则：

1. 不镜像。`design/` 下存在某个 Area，并不要求 `system_design/` 和 `implementation/` 下同时存在同名 Area；每一层只在真正产生了该层级的知识时，才拥有对应文档。
2. 按需生长。一个 Area 只有一篇文档时直接平铺成文件，不为结构完整预建文件夹；当同一问题空间自然积累出多篇文档，再升级为目录，Area 内部也可以按同样方式继续嵌套出子 Area。
3. 跨切面内容放在层根。逻辑数据模型、运行流程、技术栈、接口契约这类横跨多个 Area 的 concern，直接放在所属层的根部，不塞进某一个 Area。

固定层级提供稳定的知识入口，层内 Area 与具体文档反映项目实际形成的知识边界和体量。基础目录为空是允许的，不要求为其编造内容；DATA_MODEL.md、RUNTIME.md、TECH_STACK.md、API.md 等可选文件仍按需创建。

## 例子

想象一个很普通的“登录”。

在 Design 层，我们只关心用户输入凭证后可以登录，登录后状态能够保持，不同身份看到不同权限。

到了 System Design，问题变成了：系统怎么知道你是谁？身份验证成功以后，登录状态怎么建立？每次请求怎么确认这个人还有权限？这时可能会出现认证、会话、授权这些内部机制，但我们仍然没有决定用 Redis 还是数据库，也没有决定用哪个框架。

到了 Implementation，才开始真正选方案：密码用什么算法，Session 存 Redis 还是数据库，Cookie 怎么设置，接口怎么写，代码用什么库实现。第二年把 Redis 换掉，通常只需要动这一层；如果内部认证机制整个重做，才会上升到 System Design；如果产品决定“以后根本不用登录了”，那才是 Design 变了。

再想象一个文件上传功能。

Design 可能只是：用户可以上传文件，能看到上传进度，失败后可以重试，上传完成后文件可以被后续功能使用。

System Design 会继续考虑：上传任务有没有状态？大文件是否分块？失败以后从哪里恢复？文件什么时候算真正完成？元数据和文件内容分别由谁管理？这些已经决定了系统如何工作，但还没有规定一定要用哪家云存储。

Implementation 最后才决定：文件实际放 S3，分块大小是多少，上传使用哪套 SDK，任务状态存在哪张表，重试由哪个队列执行。以后从 S3 换成别的对象存储，只要系统机制不变，Design 和 System Design 都可以基本不动。

Design Chain 的目标，是让“我们真正想要什么”“内部怎样让它成立”和“今天具体用什么做出来”各自待在合适的位置，使人和 AI 都能清楚知道一个问题应该在哪一层解决。

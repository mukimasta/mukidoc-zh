# DEVLOG Design

DEVLOG 是项目级的开发时间线，按时间顺序持续 append。它记录项目实际上是怎么一路走到现在的，让未来的人或 AI 能快速看到开发过程中发生过哪些重要事情、遇到过哪些问题，以及项目在哪些地方发生过明显转折。

它关注的是整个项目，而不是某个模块内部的完整技术过程。一次开发可能同时修改很多模块，但 DEVLOG 只保留其中值得进入项目主时间线的部分。

通常值得记录：

* 完成了新的关键能力或阶段性成果。
* 出现了影响项目推进的重要问题。
* 实际开发或测试暴露了此前不知道的事实、限制或风险。
* 某个原有方案因为现实反馈被明显调整。
* 一次 debug 最终暴露出了更深层的系统问题。
* Evaluation 产生了会影响后续开发的重要结果。
* 项目的实现方向、开发重点或下一阶段因此发生了变化。

DEVLOG 不需要记录所有工作。普通文件修改、简单重构、小 bug、依赖升级、机械性开发过程和 Git 已经能够完整表达的变化，都没有必要重复保存。

### 记录方式

DEVLOG 按日期追加，每次开发结束后记录当次真正值得进入项目历史的内容。

格式固定为：

```markdown
### YYYY-MM-DD

1. ...
2. ...
3. ...
```

同一天的内容放在同一个日期下，用有序列表记录。每条通常 1–3 句，先说明发生了什么；如果原因、发现或影响对理解这件事很重要，再一起写进去。

好的记录应该让没有参与当天开发的人也能理解这件事为什么值得被记住。

例如：

```markdown
### 2026-09-14

1. 完成上传链路第一版并跑通大文件上传。实际测试发现文件经过应用服务器会长期占用连接和带宽，因此调整为客户端直传对象存储。
2. 断点续传测试发现浏览器刷新后客户端状态无法可靠恢复，最终改为由服务端维护上传状态。这个问题也确认了客户端进度不能作为唯一真相源。
3. 上传流程基本稳定，下一阶段可以开始处理失败恢复和清理机制。
```

这种记录保留了成果、现实反馈和项目因此发生的变化。

不好的记录更像：

```markdown
### 2026-09-14

1. 新增 UploadController。
2. 修改 UploadService。
3. 增加 3 个 API。
4. 修复上传 bug。
5. 测试通过。
```

这种内容 Git 和代码本身已经能够表达，而且无法告诉未来的人为什么这些修改重要。

另一种不好的记录是写成过细的 debug 日志。某个问题如果需要几百字才能讲清楚，应把完整过程放到对应的 information 文档，DEVLOG 只留下它对项目主线产生的结果。

### 历史性质

DEVLOG 一般情况来说只追加，不为了让它符合当前状态而重写过去。当过去的认识后来被推翻时，继续在新的日期记录变化，让时间线本身保留项目认知和实现演化的过程。

它也不承担当前状态说明。当前系统是什么样，应由对应的正式文档描述；DEVLOG 负责解释它是怎样一步步走到这里的。

它同样只记录已经发生的事情，不排布尚未执行的计划、优先级或下一步任务——这些属于 TODO，长期方向属于 ROADMAP。描述一项已完成成果的意义时，可以说明它解锁或改变了下一阶段，但那是在解释已发生的事，而不是在 DEVLOG 里安排未来的工作。

一篇好的 DEVLOG 不需要记录很多，但沿着日期读下来，应该能够快速看出项目经历过哪些关键成果、问题、发现和转折。

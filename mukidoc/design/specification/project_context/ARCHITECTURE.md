# ARCHITECTURE Design

ARCHITECTURE 用来帮助第一次接触项目的人或 AI 快速建立整个系统的骨架：系统有哪些主要部分、它们之间是什么关系、内部如何逐层展开，以及系统实际怎样运行。

ARCHITECTURE 以图为主，文字只补充图中看不出的职责、边界和重要关系。整体阅读顺序从粗到细，逐步放大同一个系统。

全文结构为：

**整体架构 → 逐层细化 → Runtime → 架构树 → 文件结构**

### 整体架构

首先从最高层画出系统边界、主要参与者、外部对象和最核心的模块关系。

这一层只需要让读者回答：

1. 谁在使用或影响这个系统。
2. 系统本身大致由什么组成。
3. 系统与外部世界是什么关系。

使用一张 Mermaid 框图即可。节点使用完整、直接可懂的名称，不使用只有作者自己知道的单字母、缩写或代号。

### 逐层细化

在整体架构之后，对同一个系统继续放大 2–3 层。

每一层只增加上一层暂时隐藏的细节，可以继续展开整张图，也可以只展开其中一个重要模块。新的图应该让读者感觉是在不断 zoom in，而不是换一种分类方式重新描述项目。

每组通常包含：

1. 一句简短说明，指出这一层正在展开什么。
2. 一张 Mermaid 架构图。
3. 必要时补充一小段图中无法直接表达的重要关系。

如果图本身已经能够说明问题，就不再用文字重复解释。

### Runtime

静态结构建立完成后，从运行时角度重新观察系统。

Runtime 选择最典型的一次完整运行过程，展示主要参与者之间的交互顺序。优先使用 Mermaid Sequence Diagram，并在保留核心信息的前提下尽量简单。

Runtime 只描述理解整体运行方式需要的步骤，不展开具体算法、接口调用、状态机或实现细节。

### 架构树

架构树从层级角度完整整理整个架构，用来补充图中不容易表达的模块职责、包含关系和边界。

每个条目对应一个真实的架构节点，不用架构树罗列设计原则或思路。已经能够从图中直接看出的连接关系不重复说明。

架构树固定使用多层有序列表：

* 全部使用有序列表。
* 尽量使用多层级列表，层次清晰。
* 每一级缩进固定为 4 个空格，条目之间不留空行。
* 使用简短、直接的语言。

### 文件结构

文件结构放在全文最后，作为最细粒度的静态视图。

使用文本目录树展示主要文件和目录，使读者能够把前面建立的逻辑架构映射到真实项目中。只展示理解项目结构所需要的层级，不展开无关的代码文件和工程细节。

ARCHITECTURE 的整体阅读体验应当是：先看到系统，再逐步看清系统，随后理解它怎样运行，最后知道这些结构实际落在哪里。

# DECISION Design

DECISION 补充记录项目中少量值得长期保留的关键决策。它保存的重点不是“最后选了什么”——结论通常能够从当前系统中直接看到——而是当时面对什么问题、默认会怎样回答，以及为什么最终没有采用那个默认。

真正值得留下的是**容易被想错的地方**。可以用一个问题判断：如果这条不写，未来的人会不会凭直觉走回我们放弃的那条路？会，说明这里存在真实的默认答案和真实的代价，应该记录。如果两种方案本来就都成立、只是任选其一，那么无论理由写得多完整，也只是留下一条个人偏好，不进入 DECISION。

适合记录的决定通常满足：

1. 存在一个自然的、多数人会直接采用的默认答案。
2. 我们偏离了这个默认，且偏离的原因无法被轻松重新推导。
3. 对未来有持续影响，未来仍可能需要理解当时为什么这样选择。
4. 即使未来决定被推翻，当时的推理过程仍然具有价值。
5. 这段思考没有更自然的文档位置。能够自然写进 Design、System Design 或 Implementation 的结论和论证，应优先留在对应文档中，DECISION 不重复它们。

任意选择中有一类例外：选择本身没有更好的答案，但它承重——其他文档、路径、工具或接口依赖它。这类情况记录的不是偏好，而是约束，说明这里为什么不能随意改动，避免未来的人把它当作可以顺手修正的东西。

DECISION 按时间顺序使用有序列表持续追加，如较为复杂，可使用多级列表。每条围绕一次完整的判断展开，简洁记录问题或背景、关键思考、最终决定，以及必要时的主要影响和适用范围，单条一般不超过 200 字。重点放在“为什么会得到这个决定”，而不是详细描述决定之后如何实现。

只记录决定发生当时真实存在的判断。如果当时的理由本来就弱、只是跟着别的选择走，或者根本没有明确理由，就照实写；不要为了让它看起来完整，事后补一套更自洽的解释。编出来的理由比空着更危险，因为它会让后来的人停止追问。

普通实现选择、临时调整、开发流水账，以及尚未发生的计划，不进入 DECISION。

已有决定被推翻时，不修改原有记录，而是追加新的决定，并记录是什么新的事实或判断推动了这次变化，使文档能够保留项目认知演化的过程。追加时指明它推翻或影响了哪一条，让按时间阅读的人能够判断旧记录是否仍然成立。
